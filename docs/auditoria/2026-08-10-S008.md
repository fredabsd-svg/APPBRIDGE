## Decisões tomadas

### D-06: Permission State Validation
- **Decisão:** Validar RevokedAt == null E (ExpiresAt == null OU ExpiresAt > now)
- **Rationale:** Duas dimensões de invalidade: revogação permanente e expiração temporal. Ambas impedem acesso. Implementado como cláusula AND para máxima segurança.
- **Alternativas:** Uma dimensão de invalidade (menos seguro), flag combinada (complexo em migrations)

### D-07: Authorization Handler Placement
- **Decisão:** ApplicationAccessAuthorizationHandler em `Infrastructure/Authorization/`, não em `Api/`
- **Rationale:** Handler é implementação de detalhe de infraestrutura (integração com IAuthorizationService), não camada de apresentação. Permite reutilização, testabilidade.

### D-08: Logging Granularity
- **Decisão:** Information para acesso concedido, Warning para negado, Error para exceção
- **Rationale:** Security event logging (ADR-0007) requer distinção entre sucesso e falha. Warning permite alertas operacionais. Error captura casos de falha do sistema.
- **Alternativas:** Todos como Information (menos segurança), todos como Debug (perde auditoria)

### D-09: GetUserApplicationsAsync Distinct
- **Decisão:** Usar `.Distinct()` na query EF Core antes de `.ToListAsync()`
- **Rationale:** Elimina duplicatas se um usuário tiver múltiplas permissions no mesmo app (teoricamente não deve existir, mas é defensivo). Agregação no banco é mais eficiente.

### R-028 (novo): ApplicationAccessHandler Depende de Route Parameter
- **Severidade:** MÉDIA
- **Descrição:** Handler obtém applicationId de `context.HttpContext.GetRouteValue("applicationId")`. Se rota não contiver parâmetro nominado corretamente, fallback é falha.
- **Impacto:** Autorização falha para qualquer endpoint que não use `{applicationId}` como nome do parâmetro de rota
- **Mitigação:** Documentação clara de convenção de rota; todos os controllers devem usar `{applicationId}`
- **Resolução:** Validação obrigatória em T-02.7 (API base) + testes de negativa em T-02.6
