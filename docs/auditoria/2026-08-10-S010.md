**Decisões tomadas (T-203):** nenhum ADR — execução de ADR-0004 e de uma consequência já registrada
em ADR-0011 §5.

1. **Filtro combinado (tenant + soft delete) no mesmo `HasQueryFilter`**, por tipo de entidade, em
   vez de dois filtros separados — é o que ADR-0011 §5 já previa, e o EF Core só permite um
   `HasQueryFilter` por tipo de qualquer forma.
2. **Reflexão para aplicar o filtro certo a cada entidade**, em vez de repetir a expressão 15 vezes
   nas classes de configuração — evita que uma entidade nova esqueça o filtro por engano; o
   `OnModelCreating` decide pela interface/classe base, não pela memória de quem escreveu a
   configuração.
3. **`ITenantContext.TenantId` nulo como "sem tenant", com filtro que devolve zero linhas** — a
   alternativa (lançar exceção quando não resolvido) quebraria qualquer código que ainda não passou
   pelo middleware de T-301; a alternativa oposta (tratar nulo como "sem filtro") reabriria
   exatamente o vazamento que ADR-0004 existe para fechar. Falhar fechado é o meio-termo seguro.
4. **`IgnoreQueryFilters()` nativo do EF Core como mecanismo de travessia**, em vez de um método
   próprio — é explícito no código (ADR-0004 item 7) e não precisa de abstração nova; a auditoria da
   travessia (RNF-017, `acting_as_provider`) fica para quando RF-075 for implementado em MVP-1.

- **Bug real encontrado durante a verificação manual — na minha própria semeadura via `psql`, não no
  código**: a primeira tentativa de popular `application`/`group`/`user_group_membership`
  manualmente usou literais numéricos (`status=1`, `launch_mode=0`, `source=0`), tratando essas
  colunas como se fossem inteiras. `\d application` revelou que `status` é `text` — o EF Core
  converte esses enums para string minúscula (`'published'`, `'remote_app'`, `'local'`), não para o
  índice numérico. O valor gravado pela minha semeadura foi literalmente a string `"1"`, que nunca
  bate com `a.status = 'published'` na consulta real gerada pelo EF Core — o endpoint respondia
  `200` com `items: []` mesmo com a permissão certa concedida, porque o filtro de status excluía
  silenciosamente a linha. Diagnosticado comparando o SQL efetivamente executado (do log
  estruturado, que já mostrava `a.status = 'published'` com um `@authorizedApplicationIds1` único —
  ou seja, a junção de autorização **já tinha encontrado** o aplicativo certo) com o valor real da
  coluna via `\d application` + `SELECT status`. Corrigido a mão no dado de verificação, não no
  código — os testes automatizados nunca passariam por esse valor errado, porque usam
  `DbContext.Applications.Add(new Application { Status = ApplicationStatus.Published })`, que já
  grava a string certa através do conversor de valor do EF Core.
